# 테스트 전략

## 커밋 단위 테스트

- 각 Phase의 최소 커밋 단위마다 `cargo test`로 유닛 테스트를 통과시킨다.
- DB 접근 로직(`games`/`tasks`/`completions` CRUD)은 인메모리 SQLite 또는 임시 파일 DB로 테스트한다 — 실제 프로덕션 DB 파일을 테스트에서 건드리지 않는다.

## API 계층 테스트

- 로컬 HTTP API(axum) 핸들러는 테스트용 서버 인스턴스에 실제 HTTP 요청(또는 axum의 `oneshot` 테스트 유틸)을 보내 응답을 검증한다 — 라우팅 로직만 목으로 우회하지 않는다.

## 기능 완성 단위 검증

- 기능이 의존하는 가장 깊은 유저 시나리오(골든 패스)까지 실제로 구동해서 확인한다. 예: "숙제 등록 → 마감 임박 시점 도달 → 알림 발송"처럼 여러 상태 전이를 거쳐야 결과가 나오는 기능은, 개별 컴포넌트 테스트만으로 완료 처리하지 않고 자동화 스크립트로 전체 흐름의 최종 결과(실제 알림 발송)까지 관찰한다.

## GUI 스파이크 테스트

- 정적 HTML+JS 스파이크는 완성된 UI가 아니므로 자동화 테스트 필수 대상은 아니지만, `fetch()` 호출이 실제 엔진 API를 왕복하는지는 수동으로 확인한다.

## 제약사항

- 크로스 플랫폼(Windows/macOS/Ubuntu) 전체 자동 CI는 후순위 — 초기에는 개발 머신(macOS) 기준으로 검증하고, 플랫폼별 서비스 등록(launchd/systemd/Task Scheduler) 등은 각 Phase에서 수동 확인한다.
