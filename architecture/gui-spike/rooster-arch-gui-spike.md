# GUI 스파이크

## 개요

본격적인 상호작용형 GUI가 아니라, 엔진 API 계약을 조기 검증하기 위한 최소 스파이크를 엔진/CLI와 병렬로 진행한다.

## 결정 사항

- **범위**: (1) 백그라운드 엔진에서 값을 제대로 읽어오는지 확인(읽기 경로), (2) 가능하면 게임 등록 같은 간단한 쓰기 경로도 왕복.
- **목적**: "완성된 GUI 제공"이 아니라 "API 설계가 실제로 동작하는가 조기 검증" — MVP 축소 취지와 충돌하지 않음. GUI 프레임워크/오버레이 동작 같은 본격 설계는 여전히 후순위.
- **구현 방식**: 정적 HTML+JS 페이지에서 `fetch()`로 로컬 API 직접 호출 — 프레임워크 선택 자체가 필요 없어 가장 빠르게 검증 가능. 나중에 실제 GUI 프레임워크를 고를 때 여기서 얻은 API 사용 경험을 참고.

## MVP 이후 GUI (참고, 본 스파이크 범위 아님)

- **상호작용형 GUI**: 숙제 등록/수정/삭제 등 완전한 관리 기능을 갖춘 일반 창 형태
- **오버레이형 GUI**: 읽기 전용, 화면 위에 항상 떠 있는 형태. 즐겨찾기 개념 — 마감 임박 여부와 무관하게 사용자가 상시 보고 싶어하는 일정을 계속 띄워두는 용도(알림 수단 아님)
- 두 GUI 모두 엔진 API를 읽기만 하거나(오버레이) 읽기+쓰기(상호작용형) 하는 클라이언트로, 엔진 자체는 두 형태를 구분하지 않음
- GUI 프레임워크는 미정 — Flutter를 대체할 가벼운 대안, 오버레이형 창 지원 여부가 후보 선정 기준

## 제약사항

- 알림 채널과는 별개: 마감 임박 알림은 OS 네이티브 토스트로 처리하고, 오버레이 GUI는 알림 수단이 아니라 열람 수단 ([notification 요구사항](../../requirements/notification/rooster-req-notification) 참조)
